# Проекция семантических результатов в Outlook Explorer

Python-сервис возвращает точные идентификаторы результата (`entry_id`,
`store_id`, `folder_entry_id`) и стабильные строковые метаданные
(`internet_message_id`, `conversation_id`, `store_name`, `folder_path`). Эти
поля сохраняются для открытия/диагностики, но не подставляются как неизвестные
ключи в штатную строку поиска Outlook.

`Explorer.Search` принимает только AQS и показывает результат в текущем окне
Outlook. Для каждого семантического результата надстройка строит наиболее узкое
переносимое условие из документированных полей:

```text
(subject:"Тема" from:"sender@example.test" received:8/11/2026)
```

Для русской поисковой локали используются `тема:`, `откого:` и `получено:`;
между полями пробел означает AND. Несколько результатов объединяются через
локализованный OR. Если отправитель отсутствует или дата не является валидной
ISO-датой, соответствующий уточнитель пропускается. Если Outlook отвергает
расширенный запрос COM-ошибкой, надстройка повторяет поиск только по темам.

## Честное ограничение

AQS в `Explorer.Search` не предоставляет надёжного exact-фильтра по бинарной
паре EntryID/StoreID. Microsoft также прямо указывает, что у метода нет callback
или программного способа получить отображённые результаты. Поэтому Outlook
может показать лишние письма с одинаковыми темой, отправителем и локальной датой;
а синтаксически принятый, но пустой запрос невозможно автоматически отличить от
реального отсутствия результатов. Полностью точная проекция потребует отдельной
MAPI Search Folder/DASL на каждый store либо записи уникального свойства в
письма; второй вариант для этого проекта запрещён.

Запрос ограничен восемью условиями и 900 символами: более длинные generated AQS
на некоторых сборках Microsoft 365 дают пустое представление без ошибки.
